# UI DESIGN RULES

## 1. Призначення

Цей документ визначає базові UX/UI-правила для освітніх вебпроєктів.

Він використовується для:

- навчальних сайтів;
- інтерактивних симуляторів;
- тренажерів;
- тестів;
- довідкових матеріалів;
- інтерактивних таблиць;
- навчальних карток;
- інформаційних панелей;
- мобільних версій освітніх сервісів.

Головна мета: створювати зрозумілі, сучасні та впізнавані інтерфейси без шаблонного AI-дизайну.

---

# 2. Основні принципи

## 2.1. Зрозумілість важливіша за декоративність

Користувач повинен одразу розуміти:

- де він знаходиться;
- що може зробити;
- що є головним;
- що відбудеться після натискання;
- як повернутися назад;
- який результат він отримав.

Декоративний елемент не повинен конкурувати з навчальним змістом.

---

## 2.2. Інтерфейс не повинен виглядати шаблонним

Не використовувати автоматично:

- великий hero-блок на кожній сторінці;
- три однакові картки в ряд як універсальне рішення;
- беззмістовні градієнти;
- декоративні світіння;
- випадкові glassmorphism-ефекти;
- надмірно округлені блоки;
- великі порожні області;
- величезні заголовки без функціональної потреби;
- однакову композицію на всіх сторінках.

Кожен layout повинен відповідати змісту сторінки.

---

# 3. Anti-AI Design Rules

Перед створенням інтерфейсу необхідно перевірити, чи не використовується типове AI-рішення лише тому, що воно часто зустрічається.

## Заборонено без функціональної причини

- gradient mesh;
- glow навколо кожної кнопки;
- декоративні орби;
- випадкові floating cards;
- glass panels;
- масове використання blur;
- 3D-іконки без системи;
- випадкові емодзі як UI-іконки;
- кілька різних стилів карток на одній сторінці;
- нескінченні секції з однаковою структурою;
- надмірні тіні;
- pseudo-premium темні інтерфейси без потреби.

## Замість цього

Використовувати:

- чисту сітку;
- чітку ієрархію;
- контрольовані акценти;
- достатні відступи;
- зрозумілі стани;
- якісну типографіку;
- логічні групування;
- різні композиції для різних типів контенту.

---

# 4. Design Tokens

Усі стилі повинні будуватися через дизайн-токени.

Структура:

```text
Primitive
↓
Semantic
↓
Component

```

## 4.1. Primitive tokens

Містять фактичні значення.

Приклад:

```text
green-700
green-600
green-100

neutral-950
neutral-800
neutral-600
neutral-200
neutral-100
neutral-50

```

Primitive token не повинен використовуватися безпосередньо в компоненті.

---

## 4.2. Semantic tokens

Описують функцію кольору.

Приклад:

```text
color-primary
color-primary-hover
color-secondary

surface-page
surface-card
surface-muted

text-primary
text-secondary
text-muted
text-inverse

border-default
border-strong

status-success
status-warning
status-error
status-info

```

---

## 4.3. Component tokens

Використовуються конкретними компонентами.

Приклад:

```text
button-primary-background
button-primary-background-hover
button-primary-text

card-background
card-border

input-background
input-border
input-border-focus

```

---

# 5. Заборона випадкових значень

Не використовувати без причини:

```css
color: #183c31;
margin-top: 27px;
border-radius: 13px;

```

Якщо значення повторюється, воно повинно бути токеном.

Особливо це стосується:

- кольорів;
- spacing;
- typography;
- border-radius;
- shadow;
- transition;
- container width.

---

# 6. Типографіка

Типографіка повинна створювати чітку інформаційну ієрархію.

Рекомендована структура:

```text
Display
H1
H2
H3
H4
Body Large
Body
Body Small
Caption
Label

```

## Правила

Не використовувати занадто багато розмірів шрифту.

Не створювати різницю між рівнями заголовків лише жирністю.

Заголовок повинен бути помітно відмінним від основного тексту.

Для довгого тексту:

```text
line-height: приблизно 1.45-1.65

```

Ширина текстової колонки:

```text
приблизно 60-75 символів

```

Не розтягувати навчальний текст на всю ширину великого екрана.

---

# 7. Spacing System

Використовувати єдину шкалу відступів.

Наприклад:

```text
4
8
12
16
20
24
32
40
48
64
80

```

Не використовувати випадкові:

```text
17px
29px
37px

```

без обґрунтованої причини.

---

# 8. Layout

Основний контент повинен мати контрольовану максимальну ширину.

Приблизний орієнтир:

```text
max-width: 1200-1440px

```

Залежно від типу сторінки.

Для текстових матеріалів використовувати значно вужчу колонку.

---

# 9. Visual Hierarchy

На екрані повинен бути один домінантний рівень уваги.

Не можна одночасно робити акцентними:

- заголовок;
- три кнопки;
- банер;
- чотири картки;
- ілюстрацію;
- sidebar.

Користувач повинен швидко визначати головну дію.

---

# 10. Картки

Картка використовується лише тоді, коли елемент справді є окремою функціональною або смисловою одиницею.

Не загортати кожен текстовий блок у картку.

Не використовувати однакову сітку карток для будь-якого типу контенту.

Можливі альтернативи:

- список;
- таблиця;
- accordion;
- tabs;
- timeline;
- featured block;
- split layout;
- navigation panel;
- comparison;
- stepper.

---

# 11. Buttons

Основні типи:

```text
Primary
Secondary
Tertiary
Danger
Icon button

```

На одному екрані бажано мати лише одну чітку Primary action.

## Стани

Кнопка повинна підтримувати потрібні стани:

```text
Default
Hover
Focus
Active
Disabled
Loading

```

Для toggle/select:

```text
Selected

```

---

# 12. Forms

Поле повинно мати:

- label;
- зрозумілий placeholder лише за потреби;
- focus state;
- error state;
- пояснення помилки;
- disabled state, якщо потрібний.

Placeholder не замінює label.

Помилка:

```text
Неправильно:
Помилка

Правильно:
Введіть число від 1 до 100.

```

---

# 13. Icons

Для функціональних елементів використовувати одну систему SVG-іконок.

Наприклад:

- Lucide;
- Material Symbols;
- інша узгоджена бібліотека.

Не змішувати кілька стилів іконок.

Emoji не використовувати як системні UI-іконки.

Emoji допускаються в навчальному контенті, якщо вони допомагають сприйняттю.

---

# 14. Border Radius

Не робити всі блоки максимально округленими.

Використовувати невелику кількість значень:

```text
small
medium
large
pill

```

Pill використовувати лише для:

- tags;
- chips;
- status;
- компактних controls.

---

# 15. Shadows

Тіні повинні допомагати визначити рівень елемента.

Не використовувати декоративні сильні тіні без потреби.

Рекомендовано максимум:

```text
shadow-sm
shadow-md
shadow-lg

```

---

# 16. Motion

Анімація повинна пояснювати зміну стану.

Використовувати для:

- hover;
- відкриття/закриття;
- зміни стану;
- переходу між кроками;
- появи feedback.

Не використовувати постійну декоративну анімацію без змісту.

Обов'язково підтримувати:

```css
@media (prefers-reduced-motion: reduce)

```

---

# 17. Accessibility

Цільовий стандарт:

```text
WCAG 2.2 AA

```

## Контраст

Основний текст:

```text
мінімум 4.5:1

```

Великий текст:

```text
мінімум 3:1

```

UI-компоненти:

```text
мінімум 3:1

```

---

# 18. Focus

Кожен інтерактивний елемент повинен мати видимий focus state.

Заборонено:

```css
outline: none;

```

без альтернативного focus indicator.

---

# 19. Keyboard Navigation

Основний функціонал повинен бути доступний без миші.

Перевірити:

```text
Tab
Shift + Tab
Enter
Space
Escape
Arrow keys

```

залежно від компонента.

---

# 20. Touch Targets

Мінімальна зона взаємодії:

```text
24 × 24 px

```

Для основних мобільних кнопок бажано:

```text
44 × 44 px або більше

```

---

# 21. Responsive Design

Проєктувати не лише desktop.

Обов'язково перевіряти:

```text
mobile
tablet
desktop
large desktop

```

Не просто зменшувати desktop layout.

На мобільному допустимо:

- змінювати порядок блоків;
- приховувати другорядні декоративні елементи;
- переводити grid у список;
- змінювати sidebar на drawer;
- використовувати accordion;
- скорочувати допоміжний текст.

---

# 22. Educational UX

Навчальний інтерфейс має особливі вимоги.

Головний принцип:

> Користувач повинен розуміти не лише що натиснути, а й чого він навчається.

---

# 23. Одна навчальна дія за раз

Не перевантажувати екран одночасно:

- теорією;
- формулами;
- тестом;
- підказками;
- поясненнями;
- статистикою;
- додатковими матеріалами.

Краще використовувати послідовність.

---

# 24. Навчальна структура

Для тренажерів рекомендований сценарій:

```text
Завдання
↓
Дія користувача
↓
Результат
↓
Пояснення
↓
Наступний крок

```

---

# 25. Feedback

Після відповіді користувач повинен одразу отримати feedback.

Недостатньо:

```text
Правильно

```

Краще:

```text
Правильно.

12 × 5 = 60, тому відповідь 60.

```

При неправильній відповіді не показувати лише червоний колір.

---

# 26. Помилка як частина навчання

Помилка користувача не повинна виглядати як системна аварія.

Не використовувати агресивне:

```text
ERROR
FAILED
WRONG

```

Краще:

```text
Спробуйте ще раз.

```

або

```text
Зверніть увагу на знак перед дужками.

```

---

# 27. Підказки

Підказка не повинна одразу давати готову відповідь.

Рекомендована система:

```text
Підказка 1 - напрям
Підказка 2 - правило
Підказка 3 - частина розв'язання

```

---

# 28. Progress

У багатокрокових вправах показувати прогрес.

Наприклад:

```text
4 із 10

```

або progress bar.

Користувач повинен розуміти обсяг завдання.

---

# 29. Результати тестування

Результат повинен містити не лише бал.

Бажано показувати:

```text
результат;
кількість правильних;
кількість помилок;
теми, де були помилки;
можливість повторити;
можливість переглянути пояснення.

```

---

# 30. Формули

Математичні та хімічні формули повинні відображатися як формули, а не як звичайний текст.

Бажано використовувати:

```text
KaTeX
MathJax

```

або інший семантично коректний renderer.

---

# 31. Таблиці

Складні таблиці повинні підтримувати:

- горизонтальний scroll на малих екранах;
- sticky header за потреби;
- достатній контраст рядків;
- чіткі заголовки колонок.

Не перетворювати таблицю на картки лише заради модного mobile UI, якщо втрачається можливість порівняння.

---

# 32. Інтерактивні таблиці

Для інтерактивних таблиць, наприклад періодичної системи:

користувач повинен легко відрізняти:

```text
available
hover
selected
disabled
highlighted
related

```

Колір не може бути єдиним способом передавання значення.

---

# 33. Симулятори

Перед початком симуляції користувач повинен розуміти:

- мету;
- початкові умови;
- доступні дії;
- критерій успіху.

Після завершення:

- результат;
- наслідки вибору;
- пояснення;
- можливість повторити.

---

# 34. Gamification

Не додавати гейміфікацію лише для декоративності.

Бали, badges, levels або streaks мають бути пов'язані з реальною навчальною активністю.

Не використовувати маніпулятивні механіки.

---

# 35. Language

Текст інтерфейсу має бути коротким і конкретним.

Перевага:

```text
Перевірити відповідь

```

замість:

```text
Натисніть тут, щоб перевірити, чи правильно ви виконали це завдання

```

---

# 36. Empty States

Порожній екран не повинен виглядати як помилка.

Приклад:

```text
Тут поки немає збережених результатів.

Пройдіть перший тест, і він з'явиться тут.

```

---

# 37. Loading

Якщо операція займає час, показувати зрозумілий loading state.

Не залишати інтерфейс без реакції після натискання.

---

# 38. Error Handling

Помилка повинна пояснювати:

```text
що сталося;
що можна зробити;
чи збережені дані.

```

Не показувати користувачу технічні stack trace.

---

# 39. Content Hierarchy

Навчальна сторінка повинна мати зрозумілу структуру.

Наприклад:

```text
Назва
Короткий вступ
Основний матеріал
Приклад
Практична дія
Пояснення
Додатковий матеріал

```

Не змішувати всі рівні контенту в один візуально однаковий потік.

---

# 40. Design Variance

Різні типи контенту можуть мати різні композиції.

Наприклад:

```text
теорія → article layout

матеріали → list/grid

симулятор → workspace

тест → focused step layout

результати → dashboard

довідник → navigation + content

порівняння → table

```

Єдність дизайну не означає однаковість сторінок.

---

# 41. Brand Consistency

У межах одного проєкту повинні бути стабільними:

- палітра;
- типографіка;
- іконки;
- radius;
- buttons;
- forms;
- spacing;
- feedback states;
- навігація.

---

# 42. Заборонено

Без окремого дизайнерського рішення не використовувати:

```text
5+ акцентних кольорів;
3+ гарнітури шрифтів;
випадкові gradients;
випадкові shadows;
випадкові border-radius;
emoji замість UI-іконок;
різні стилі кнопок на різних сторінках;
надмірну кількість badges;
надмірну кількість карток;
текст поверх складного зображення;
низький контраст;
hover-only функціонал;
приховану навігацію без причини.

```

---

# 43. QA: перевірка перед завершенням сторінки

## Design

□ Є чітка візуальна ієрархія.

□ Зрозуміла головна дія.

□ Немає випадкових кольорів.

□ Немає випадкових spacing values.

□ Немає зайвих карток.

□ Немає шаблонного AI-layout.

□ Типографіка узгоджена.

□ Відступи системні.

□ Іконки одного стилю.

□ Тіні та radius використовуються послідовно.

---

## UX

□ Користувач розуміє, що робити.

□ Інтерактивні елементи виглядають інтерактивними.

□ Є feedback після дії.

□ Помилки пояснюють наступний крок.

□ Loading state передбачений.

□ Empty state передбачений.

---

## States

□ Default.

□ Hover.

□ Focus.

□ Active.

□ Disabled.

□ Loading, якщо потрібний.

□ Error, якщо потрібний.

□ Selected, якщо потрібний.

---

## Accessibility

□ Контраст відповідає WCAG AA.

□ Focus видимий.

□ Keyboard navigation працює.

□ Touch targets достатнього розміру.

□ Інформація не передається лише кольором.

□ Є semantic HTML.

□ Images мають alt там, де він потрібний.

---

## Responsive

□ Mobile перевірений.

□ Tablet перевірений.

□ Desktop перевірений.

□ Немає горизонтального scroll без потреби.

□ Навігація працює на mobile.

□ Основні дії доступні без zoom.

---

## Educational UX

□ Завдання сформульоване однозначно.

□ Користувач розуміє мету.

□ Feedback має навчальну цінність.

□ Помилка не карає користувача.

□ Підказка не видає відповідь одразу.

□ Прогрес зрозумілий.

□ Результат пояснюється.

□ Є можливість повторної спроби.

---

# 44. Anti-Slop Final Check

Перед завершенням дизайну поставити питання:

1. Чи виглядає ця сторінка так, ніби її автоматично згенерував AI?
2. Чи можна прибрати хоча б один декоративний елемент без втрати змісту?
3. Чи кожна картка справді потрібна?
4. Чи є композиція, а не просто набір блоків?
5. Чи легко побачити головне?
6. Чи однакові компоненти справді однакові?
7. Чи немає надмірної декоративності?
8. Чи відповідає layout типу контенту?
9. Чи зручно користуватися сторінкою, а не лише дивитися на неї?
10. Чи має продукт власний характер?

Якщо відповідь на останнє питання "ні", дизайн ще не завершений.
